## Synthesis: decisions that should influence the next implementation

**D01 — Compose the whole screen before tuning a control.** The previous rejected PR #30 changed narrow details but did not change the experience at first glance. Evaluate entire desktop shell and phone chat as connected compositions (header, navigation, conversation, composer, contextual tools, states), including populated threads. A design must be visibly and functionally more intentional.

**D02 — Two deliberately different expressions.** iOS: touch-reachable navigation and content-first gestures, calm glass *at controls*, readable sheets and engaging transitions that respect reduced effects. Desktop: precision hierarchy, sophisticated information density, intentional context/split surfaces, keyboard-first interaction. The shared Eclipse, lime signal and product capabilities unify them.

**D03 — Elevated routing as a recognizable Lumen capability.** Unlike generic chat apps, Lumen selects, explains and reroutes models. Explore a distinct route/status presentation integrated into reading and composing without adding redundant panels or consuming large space.

**D04 — Real functionality is the art-direction constraint.** Preserve the actual Auto/Layouts/model management, Tools/Projects/Library, Canvas, Compare, repo and voice/privacy contexts as designed constituents. "Simplify" by changing where information is presented, not eliminating it.

**D05 — Visual review must be unconditional, not rationalized.** Use real-component iOS welcome/populated chat/composer/drawer/Add/model/hub, and desktop welcome/chat/sidebar/tool/Settings/overlay, matching the unmodified branch. **If a user can't immediately see and value the composition improvements without our explanation, it fails.**

**D06 — Technical feasibility is not implementation permission.** Research guides *creative decisions*; source ownership, actual model/data semantics, performance/keyboard tests and explicit user visual approval gate implementation and release. Exclude native-only capabilities rather than simulating fake results.

## Bounded concept exploration, before merge

Sketch **two composition-level alternatives per platform** in the actual app using reversible, isolated source branches/toggles, and keep full control paths:

- **iOS A — Seamless workbench:** immersive content canvas, lightweight contextual header, one anchored composer with integrated route feedback, dedicated sheet layer for secondary tasks.
- **iOS B — Task-oriented studio:** contextual navigation built around active task/project, clearer multi-step tool entrance, connected route/composer relationship, stable chat reader. Not an extra permanent tab bar.
- **Desktop A — Editorial workspace:** calmer navigation column + strongly composed reading/writing canvas + purpose-built contextual tool inspector only when useful.
- **Desktop B — Professional command desk:** rich but disciplined task header, model/source context and direct keyboard actions, adaptable side surfaces and less modal switching; the conversation remains visually dominant.

These are **working hypotheses, not visually approved mockups or fixed layouts**. Compare feature access, responsiveness, dense content, implementation cost and actual before/after full-screen visuals. A chosen hybrid must remain coherent across all three themes.

## Outstanding research and test limitations

Apple materials and gestures in these sources describe actual native apps; Lumen's conditional browser glass does not reproduce them exactly. Linear and Raycast examples illustrate their authors' intent and outcomes, not proof of Lumen quality. Further research needs direct screen inspection for components beyond documented articles; do not falsely claim access to product internal files or real-device videos. Real Lumen screenshot review must continue independently in browser CI, and user aesthetic approval is mandatory before any substantial production merge.
