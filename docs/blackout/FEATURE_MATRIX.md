# Blackout capability research: 9Router → Lumen

Research checkpoint: **20 October 2026**. This is a source-grounded comparison and delivery proposal, not evidence that new functionality has shipped or that provider integrations have been live-tested. It supports Blackout Phase 1 and the complete master directive §5. Identity/core/final aesthetic approval gates remain binding.

## Evidence and version boundaries

- **9Router source inspected:** `decolua/9router`, default branch `master`, commit [`87a74e1bda3677193c6f71a7e2100c90311f0689`](https://github.com/decolua/9router/commit/87a74e1bda3677193c6f71a7e2100c90311f0689), committed 15 October 2026. Its package version is **0.5.104** [R02].
- **Latest public GitHub release observed:** [`v0.5.35`](https://github.com/decolua/9router/releases/tag/v0.5.35), published 16 July 2026. Master, npm versions, release tags, old documentation and third-party screenshots are different evidence; do not silently combine them as one tested release.
- The official [website](https://9router.com) and pinned README [R01] describe a gateway for external coding tools. Claims such as “40+ providers,” “100+ models,” “20–40% savings,” “lossless,” or “zero downtime” are **advertised**, not independently measured in this research.
- The architecture document [R03] is dated 6 February 2026 and describes `db.json`/`usage.json`. Current `localDb.js` and `usageDb.js` are compatibility shims to a **SQLite-based** layer [R17]. Current source takes precedence over that older persistence description.
- **Lumen inspected:** PR #34 documentation branch based on `main` `c4b55781f1046e8abd75966ecb6c565327a1d62a`; source tree read without changing or executing provider integrations. `src/lib/ai/provider-config.js` enumerates **32 AI providers**: four core providers plus 28 additional configurations. That count does not establish identical availability, subscription access or model coverage with 9Router.
- Lumen's existing verification is recorded in the independent [Model Picker validation map](../MODEL_PICKER_VALIDATION.md), root implementation plan/handoff and existing test files. **No new application, provider, security, performance or browser test was run for this document.** “Already implemented and verified” below means existing source plus recorded project evidence, not a fresh research-session test pass.
- No 9Router executable, downloader, package, extension, OAuth flow, subscription token, real credential or paid inference was used. Public source copies are outside the checkout under `/tmp/lumen-blackout-research/`.

## Decision vocabulary

| Code | Classification | Meaning here |
|---|---|---|
| V | Already implemented and verified | Preserve the existing Lumen contract; do not rebuild it to imitate another UI. Recorded verification must be refreshed when implementation changes. |
| N | Needs improvement | A grounded gap with a proposed Lumen-native improvement. A proposal is not an implemented feature or a completed roadmap item. |
| E | Approved for equivalent implementation | Use only after the specific capability/delivery contract is selected in the maintained plan; **no unselected feature is given E automatically**. |
| A | Requires major architectural changes | A new connection model, gateway, trust boundary or persistent service must be designed and reviewed first. |
| D | Requires a user decision | A material product/security/permission/cost choice remains; do not infer it from a reference screenshot. |
| X | Intentionally excluded with justification | An unsafe or inappropriate *method* is excluded; preserve any legitimate equivalent benefit where feasible. |
| U | Unverified in the reference product | Documentation/marketing is insufficient to assert the exact behavior, guarantee or performance. |

Effort is relative **S/M/L/XL**, not a delivery-time estimate. Priority: **P0 preserve**, **P1 valuable browser-native candidate after the relevant design gate**, **P2 optional/measure first**, **G explicit architecture/permission decision**, **X excluded method**. No feature decision in this research creates spending authorization or changes project weights.

## Recommended first capability milestones

These are research recommendations for the maintained plan, not automatic implementation before identity approval.

1. **Provider state overview (F02–F04/F17):** highest information value with existing data and no new inference; reuse the canonical registry/settings owner.
2. **Redacted route receipt (F28):** make Auto and recovery understandable using existing decisions/events; start without persistent history.
3. **Portable Layout recipes (F30):** share reproducible routing setup without credential transfer or new infrastructure.
4. **Usage provenance/estimates (F15–F18):** only after defining exact historical read/retention/price contracts; reuse present usage accounting rather than inventing metrics.

Do not schedule a browser-only CLI gateway, upstream multi-account token vault, automatic subscription OAuth harvesting or external compression processor as a routine UI milestone. Those need separate explicit architecture/security/operational decisions. Model-level rotation and tool-output compression are optional, workload-dependent choices, not replacements for already working Auto and compaction.

## Threat-model starting points for selected additions

| Boundary | Main abuse/failure cases | Required controls before implementation |
|---|---|---|
| Provider overview / route receipts | Cross-account metadata; prompt/key leakage in provider errors; hidden paid probes; false account-capacity claims | Existing opaque account/config scope; allowlisted structured metadata; redact before truncation; no raw payload storage; explicit probes; unknown/stale labels; finite retention. |
| Import/export | Secret exfiltration; malicious JSON/prototype keys; arbitrary host injection; destructive settings replacement | Credential-free field allowlist, bounded parser, schema/version validation, dry-run/diff, atomic import, no executable content, preserve old settings and unavailable model assignments. |
| Multi-connection credentials/OAuth | Wrong-account refresh, token leakage, credential rotation bypass, paid fallback without consent | Stable connection identity in every state/cache/request path, supported OAuth clients/scopes, encrypted storage design where selected, revocation/cancellation, per-connection billing permissions, finite recovery. |
| Inbound gateway / local companion | Unauthenticated use, SSRF, cross-user requests, exposed local listener, unbounded cost or tool replay | Explicit trust architecture, least-privilege inbound keys/allowlists, safe bind/TLS policy, redirect denial, body/time/concurrency/budget limits, no raw logs, tenant isolation and idempotency/side-effect contracts. |
| External compression | Private prompt/code transfer; changed meaning; added latency/cost; compressor outage | Explicit destination/data consent, no default data transfer, privacy compatibility, original-output retention, reversible opt-in, timeout/failure passthrough, measured semantic and latency acceptance. |

These are design requirements, not a penetration-test result or a claim that 9Router has particular exploitable vulnerabilities.
